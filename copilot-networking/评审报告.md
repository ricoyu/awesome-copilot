## P0（生产环境一旦触发, 服务直接不可用）

### P0-1 同一个进程里第二次使用 HttpUtils 必定报错：每次请求结束都把全局共享连接池关掉【实测】

```java
// AbstractRequestBuilder.java:597
try (CloseableHttpClient httpClient = buildHttpClient()) {
```

- 现象（surefire 报告原样输出，`HttpUtilsConnectionPoolBugTest`）：
  ```
  HttpUtils P0-1 复现: first=success, second=IllegalStateException: Connection pool shut down
  ```
  测试起本地 HTTP 服务，第一次 `HttpUtils.get(url).request()` 成功，第二次（以及之后所有）抛 `Connection pool shut down`。整个进程只有第一次请求能成功。
- 原因链条（三段，都查证过）：
  1. `connectionManager` 是 static 的，全类共享（AbstractRequestBuilder.java:115, 136）；
  2. `buildHttpClient()` 用 `setConnectionManager(connectionManager)` 构建客户端（:275）。翻 HttpClientBuilder 4.5.13 源码（HttpClientBuilder.java:1216-1246）：只要连接管理器是自己传的且没声明 `connManagerShared(true)`，builder 就会往客户端的 closeables 列表里塞一条 `cm.shutdown()`；
  3. 于是 try-with-resources 走到 `httpClient.close()`（InternalHttpClient.java:197-201 逐个执行 closeables）→ 关的是**那个 static 共享池本身**。池关了不会自己复活，后面所有请求集体报废。
- 影响：这不是"高并发才有"的问题，是最简单的顺序调两次接口就复现。copilot-search 的 ElasticPipelineBuilder、OAuth2 测试等所有 HttpUtils 调用方，只要一个进程里发第二个请求就会遇到这个故障。
- 怎么改（二选一，推荐 ①）：
  ① 客户端也做成 static 单例（一个进程一个 CloseableHttpClient 是 Apache 官方推荐用法，超时差异用**每个请求** `requestBase.setConfig(RequestConfig)` 携带，不是每个客户端一套），退出时由 JVM 回收或注册 shutdown hook 统一关；
  ② 不改整体架构, 只做一个改动就能让连接池不再被关闭：`buildHttpClient()` 里加 `.setConnectionManagerShared(true)`——这样 client.close() 不会连带关池。

### P0-2 除 400/405/500 外的一切错误状态码都被当成功返回【实测】

```java
// ErrorUtils.java:13-22
public static void checkError(int statusCode, String reason) {
    switch (statusCode) {
        case 200: break;
        case 405: throw new BusinessException(METHOD_NOT_ALLOWED, reason);
        case 500: throw new BusinessException(INTERNAL_SERVER_ERROR, reason);
        case 400: throw new BusinessException(BAD_REQUEST, reason);
    }   // 401/403/404/502/503... 落到 switch 结尾, 什么都不做
}
```

- 现象（探针原样输出）：服务端返回 `404 + {"error":"not found"}`，`request()` 把这个错误体当正常结果返回：`404 response returned as success: [{"error":"not found"}]`。
- 影响：token 过期返回 401、网关故障返回 502，调用方全都察觉不到出过错；配合 `.responseType(Xxx.class)` 时，Jackson 会把错误响应的 JSON 反序列化成字段全为 null 的"成功"对象，错误一路传到下游模块才被发现，排查起点和真正的出错点隔了几个系统。这是最容易在联调里耗一整天的一类 bug。
- 怎么改：`statusCode >= 200 && statusCode < 300` 放行，其余一律抛（异常消息带上状态码和响应体前 N 字节），并保留 BusinessException 的类型区分（见 P1-6，异常现在会被外层 catch 重新包装，类型信息在调用方视角丢了）。

### P0-3 URL 里已编码的查询参数会被二次编码，参数送达时变了样【实测】

```java
// AbstractRequestBuilder.java:571-575
MultiMap multiMap = urlParts.paramMap();   // 值还是 %xx 形式
params.putAll(multiMap);
List<NameValuePair> pairs = toNameValuePairs(params);
builder.setParameters(pairs);              // URIBuilder 再编码一遍
```

- 现象（探针抓到的服务端原始 URI）：请求 `http://127.0.0.1:18702/idx?type=doc%20x&t2=ab%3Dcd`，服务器实际收到 `/idx?type=doc%2520x&t2=ab%253Dcd`——`%20`（空格）变成 `%2520`，即百分号自己又编了一次。
- 原因：teardown 拆出来的参数值不做解码，原样丢给 `URIBuilder.setParameters`，而 URIBuilder 的职责就是"把你们给我的原始文本编码成 URL"。两边都认为自己给的是"未编码原文"，结果编码了两层。
- 影响：凡是 URL 带查询串且值含中文/空格/特殊字符（做过 URL 编码）的 GET 请求，参数值全部变形（空格变成字面的 %2520 这类双重编码文本）。搜索、过滤、带签名 token 的接口受影响最重。而且哪怕你没用过 addParam，只要参数写在 url 字符串里，就会被再编码一次。
- 怎么改：在 paramMap() 或合并前对每个值先 `URLDecoder.decode(v, UTF_8)`，让 URIBuilder 做唯一一次编码；或者干脆放弃"拆再拼"，整 URL 交给 `new URI(url)`，addParam 的参数用 `URLEncodedUtils.format` 追加。

## P1（正确性 / 可靠性）

### P1-1 PATCH 在枚举里，不在 switch 里：一调就 NPE【实测】

`HttpMethod.java:30` 有 `PATCH`，`AbstractRequestBuilder.buildHttpRequest` 的 switch（:526-548）只到 HEAD/OPTIONS/TRACE，没有 PATCH 分支也没有 default。实测异常链：

```
java.lang.NullPointerException: Cannot invoke "HttpRequestBase.addHeader(...)" because "request" is null
    at AbstractRequestBuilder.addHeader(AbstractRequestBuilder.java:698)
    at AbstractRequestBuilder.buildHttpRequest(AbstractRequestBuilder.java:550)
```

（method 传 null 是同样的下场。）同一个 switch 还漏了 PATCH 对应的 `HttpPatch` 实体语义：即使补个 `new HttpPatch(uri)` 也要归进 `HttpEntityEnclosingRequestBase` 那条 addBody 判断链（request():587 只认 Post/Put）。建议：加 PATCH 分支 + default 抛 `IllegalArgumentException("unsupported method: " + method)`，别让 null 往下漏。

### P1-2 同名多值参数变成 `"[java, go]"` 这种带方括号字符串【实测】

```java
// AbstractRequestBuilder.java:483-484
List valueList = (ArrayList) entry.getValue();
pairs.add(new BasicNameValuePair(entry.getKey(), StringUtils.joinWith(",", valueList)));
```

本仓库自研 `StringUtils.joinWith(String, Object...)`（commons-lang StringUtils.java:88）收可变参数，这里传进去的是**一个 List 对象当作一个元素**，Guava Joiner 对它 join 等于调 toString。实测输出：`multi-value tag encodes to: [[java, go]]`——服务端收到 `tag=[java, go]`，方括号和空格都在。注释写的是"把多个值用,连接"，实际做不到。修法：`StringUtils.joinWith(",", valueList.toArray())`。

### P1-3 URL 查询参数里值带 `=` 或没有 `=` 的，被不报错地直接丢掉【实测】

```java
// UrlParts.java:72-74
String[] paramNameValue = nameValue.split("=");
if (paramNameValue.length == 2) { multiMap.put(...); }   // 不是恰好2段 → 悄悄扔掉
```

实测：`?type=a%20b&token=ab%3Dcd%3D&flag&x=1=2=3` 解析后只剩 `[type, token]`；`flag`（无值布尔参数）和 `x=1=2=3`（值里带未编码的 =，典型是 base64 尾部 `==`）都消失了，没有任何日志。修法：`split("=", 2)`，无 `=` 的按空串值保留。

### P1-4 自己手写 URL 正则而不是用 JDK 解析器, 实测有两个解析错误；teardown 返回 null 后 request() NPE

`RegexUtils.java:56` 的 `URL_REGEX` 中端口段写死 `(\d{2,})`（至少两位），host 段 `[^/?#:]*` 排除冒号（IPv6 必带）：

- 实测 1：`http://host:8/path` → `host=host port=80 path=":8/path"`（单位数端口整个解析错位）。
- 实测 2：`http://[::1]:9200/rico/_mapping` → `host="[" port=80 path="::1]:9200/rico/_mapping"`（IPv6 全毁）。
- 另外 teardown 对不合法 URL 返回 null（RegexUtils.java:69,74），request() 拿着这个 null 直接调 `urlParts.getScheme()`, 抛出 NullPointerException，报错位置和真实原因（URL 写错了）隔了十万八千里。

建议整段废弃，用 JDK 的 `new URI(url)`（必要时 commons 的 `URLEncodedUtils.parse(URI, charset)` 拿参数），非法 URL 在 `url()` 入口就抛带原文的异常。

### P1-5 FormRequestBuilder.addCookie(name,value) 硬编码域名 "sexy-uncle.com"【实测·代码】

```java
// FormRequestBuilder.java:123
cookie.setDomain("sexy-uncle.com");
```

两参版 addCookie 把 cookie 域写死成作者自己项目的域名。往 `localhost` 或任何别的站发表单时，HttpClient 的 cookie 匹配规则会因域不符直接不带这个 cookie——登录态类接口表现为"明明加了 cookie 服务端却说没收到"，排查方向还全被带偏到服务端。对照 JsonRequestBuilder 的两参版干脆没设 domain（:178-181，能按请求域正常匹配）。修法：删掉写死的 setDomain，或让两参版走 requestConfig 的 cookieSpec 让它按请求主机自动归属。顺带：JsonRequestBuilder 四参版收了 `path` 参数却写死 `cookie.setPath("/")`（:188），形参无效，两个同名类行为分叉（twin 差异）。

### P1-6 异常处理有三处互相矛盾

1. ErrorUtils.checkError 抛的 `BusinessException` 会被 request() 的 `catch (Exception e)`（:646）再包一层 `HttpRequestException`——调用方 `catch (BusinessException)` 永远捕不到，想按 401/404 分支处理只能扒 getCause。4xx（客户端错）和 5xx（服务端错）的语义在包装中丢失。
2. `if (errorCallback != null) { errorCallback.accept(e); }`（:647-648）之后**方法照常 return null**：回调里抛出的异常也会从 return null 溜走，调用方拿 null 完全不知道出过错。回调模式至少要把"出过错"这个事实保留（返回 null 前记 warn，或回调后仍抛）。
3. `log.error("", e)` 全文出现 6 处（AbstractRequestBuilder:126/521/650、FormRequestBuilder:409、HttpClientUtils:287/290）——消息为空串，日志检索时这些行连个关键词都搜不到。至少写清"什么操作失败"。
4. 状态码局部变量拼错 `statucCode`（:618-622）。

### P1-7 response 没有实体时不报错、直接返回 null；`responseType(byte[].class)` 配 `returnBytes(false)` 会 ClassCastException【实测/代码】

request() 里 `if (entity != null) {...}` 之后不提示任何东西, 直接走到方法末尾 `return null`（:624-655）。HEAD/204 响应属正常空体，null 尚可接受；但 `returnBytes` 为 true 时 `IOUtils.toByteArray(entity.getContent())` 返回流之后 **没有把内容流/连接消费归还的路径问题**这里先不论，`responseType=byte[].class` 而没开 returnBytes 时，Jackson 拿 String 反序列化 byte[] 抛 ClassCastException，一路包成 HttpRequestException——异常消息让人完全猜不到根因。建议：responseType==byte[].class 时自动按 returnBytes 处理。

## P2（性能 / 设计 / 技术债）

### P2-1 全局信任所有 HTTPS 证书 + 主机名不校验（CLAUDE.md 已知问题，仍未修）
AbstractRequestBuilder.java:120-129 静态块：`(cert, authType) -> true` + `NoopHostnameVerifier`，且没有任何 API 能让调用方关掉。中间人在公司出口网关/公共 Wi-Fi 下可无痛解密所有 https 流量。建议：默认走系统信任链，开 `trustAllCerts(true)` 显式开关（内网自签证书场景确实需要，但要"自己声明才生效"）。

### P2-2 写了却没人接线的 IdleConnectionEvictor【实测·grep 全仓库 0 引用】
`httpclient/IdleConnectionEvictor.java` 定义了空闲连接回收线程，全仓库（含 copilot-test）没有任何 `new IdleConnectionEvictor` 或对它的调用。后果：池里的 keep-alive 连接被服务端/负载均衡掐掉后连接池不知情，闲置一段时间后的第一批请求会拿到已经被对端关闭的连接（抛出 NoHttpResponseException，靠 HttpClient 默认重试机制吸收——等于每次闲置一段时间后, 第一个请求都要白白多走一轮"失败再重试"的往返）。修法两选一：接线跑 evictor（顺带 `closeIdleConnections`，它现在只调了 `closeExpiredConnections`，空闲但没有过期的坏连接照样清理不掉——这是它自身的设计缺陷），或者 HttpClientBuilder 开 `evictIdleConnections(30, SECONDS)`。另：它 `catch (InterruptedException) {}` 捕获后什么都不做, 既不记录也没恢复线程中断标志（:35-37），属于该修的小毛病。

### P2-3 每次请求 new 一个 CloseableHttpClient + new 一个 Timer
- buildHttpClient() 每次走一遍 builder→InternalHttpClient 组装（含拦截器链复制），每次 HTTP 请求平白多出几十微秒的无用开销，高 QPS 下 GC 压力明显。和 P0-1 是同一个根：客户端该单例。
- request() 里 timeout 分支（:601-611）每次 `new Timer(true)` 起线程，且任务在请求提前结束后**不 cancel**——Timer 线程要一直存活到 timeout 时刻才结束。10 万个请求就是 10 万个白白存活的线程（daemon 线程不阻止 JVM 退出，但每个线程约占 1MB 栈地址空间）。修法：`schedule` 后在 finally 里 `task.cancel()`，或者干脆删掉这套，用 RequestConfig 三件套超时（本来就有）+ 连接池级排队超时，生命周期超时用 `ClientProtocolException` 兜不住的话再议。

### P2-4 HttpClientUtils：与 HttpUtils 并行的第二套实现，问题更老更多，实际只有 1 处测试引用【实测·grep】
全仓库唯一调用点是 copilot-search 的 ESIndexTest 一行。它自带第二个 50/5 的 static 连接池；`getResult()` 里 response **不在 finally 关**（:272-295，entity==null 时直接 return ""，连接泄漏——这正是 CLAUDE.md 旧报告说的泄漏，HttpUtils 那边"修了"，这孪生副本原封没动）；`httpGetRequest(url, params)` 把完整 URL 塞进 `ub.setPath()`（:99），产出的请求目标是 `/http://host/path` 这种畸形路径【推断，构造个 URIBuilder 打印即可证】；`httpsRequest` 非 2xx 走 getInputStream 抛异常、catch 后 return null（:209-229），错误体永远读不到；`createIgnoreVerifySSL` 用 `SSLContext.getInstance("SSLv3")`（:240）——SSLv3 协议在现代 JDK/openssl 策略里默认禁用，JDK21 上能否 init 成功未实测【推断】，但无论如何它现在没有任何存在的理由, 应该删掉。建议：整类 @Deprecated，调用点迁 HttpUtils，下个迭代删除。（`java.awt.image.RescaleOp` 误导入在 ErrorUtils:6，顺手删。）

### P2-5 GET/HEAD/DELETE 也带 Content-Type: application/json【代码】
HttpUtils.java:43/63/125：所有 get/delete 都 addHeader(CONTENT_TYPE,...)。GET 没有请求体，Content-Type 毫无意义，个别严格网关会因此 400。delete(url) 带 body 时 HttpClient 的 HttpDelete 根本不设 entity（buildHttpRequest 的 DELETE 分支不支持 body，request():587 的 addBody 判断也不含 Delete）——想按 ES _search 惯例用 DELETE 请求带请求体的用户, 会遇到"body 不发出去也不报错"【推断·代码路径明确：jsonBody 无处可去】。

### P2-6 `scheme(HTTPS)` 忘 `port(443)` → 请求打到 80
port 字段默认 80（:164），走 host/port 分段构建时不看 scheme 修正端口（buildUrlParts:501-507 直接 setPort(port)，默认值恒非 null，永远盖掉 https 的 443 推断）。整 URL 走 teardown 那支反而有 443 默认（RegexUtils.java:82-84）——同一语义两套路径行为不一致。修法：分段路径里 scheme==HTTPS && 用户未显式设过 port → 443。

### P2-7 表单 Content-Type 不带 charset、文件上传 part 的 Content-Type 用错
- `form(url)` 预置头 `application/x-www-form-urlencoded`（HttpUtils.java:139，无 charset）。实测确认请求头原样送达（无 charset）；UrlEncodedFormEntity 实际按 UTF-8 编码 body。HTTP 表单规范默认字符集是 ISO-8859-1，严格解析的服务端遇到中文表单字段会乱码【推断：需一个按 header 声明解析的 servlet 容器复现，Tomcat 系默认 URIEncoding 已改 UTF-8 所以多年来没人碰到这个问题】。修法：预置头改成 `application/x-www-form-urlencoded;charset=UTF-8`。
- FormRequestBuilder.java:390：multipart 里**文本 part** 的 Content-Type 写成 `multipart/form-data`（这是整个请求的类型，不是 part 的，part 应是 `text/plain;charset=UTF-8`）。且非文件分支（:407）`new UrlEncodedFormEntity(params)` 用无 charset 构造器，依赖 4.5 默认 UTF-8，升级 HttpClient 5 时这是行为变更点。
- `formData(String, Object)` 用 ConcurrentHashMap，null 值 put 直接 NPE，而 file(String, String) 里 IOUtils.readFile(fullFilename) 文件不存在时**抛的是 IllegalArgumentException("file not found!")**（IOUtils.java:300 语义：返回 File 对象而非读字节）——注意这个 `file(String paramName, String fullFilename)` 名字让人以为是上传文件内容，实际只是把路径转 File 再走 fileUpload 分支，行为与 `file(paramName, new File(path))` 相同，无害但易误读；真正读字节的 readFileAsBytes 在隔壁。

### P2-8 cookieStore 写了但没有实际作用
每个 builder 实例一个 BasicCookieStore（:238），而 builder 都是 `HttpUtils.get(...)` 现场 new 的——服务端响应里的 Set-Cookie（会话、CSRF token）存进了一个马上被丢弃的 store，下一个请求（新 builder）什么都不带。想要会话粘性的用户要么手动把 token 从响应里抠出来 bearerAuth，要么需要给 builder 暴露共享 CookieStore 的口子。当前文档/注释完全没提这一点，`addCookie` 系列方法给人的错觉是"cookie 会维护"。

### P2-9 不指定 retries 时行为与指定后不同源【实测·HttpClientBuilder 源码】
retries==null 时走 HttpClientBuilder 默认的 `DefaultHttpRequestRetryHandler.INSTANCE`（HttpClientBuilder.java:1142-1146：3 次、非幂等已发出请求不重试）；一旦 `retries(n)` 则换成 `StandardHttpRequestRetryHandler(n, requestSentRetryEnabled)`。两者对"哪些异常算可重试"的名单不同（比如 redirect 处理不同），同一个 API 两次调用配置路径不同、结果不同，属于"看起来只是换个次数"的隐性行为切换。建议：始终显式构建同一个 handler。

## 外围工具类（并行评审代理报出 15 条，以下逐条亲测复核后的采信结果）

### P1-8 IpAddressMatcher 拿 `InetAddress.getByName` 当解析器用 = 白名单可被 DNS 绕过【实测】

`matcher/IpAddressMatcher.java:87-94`：`parseAddress` 直接 `InetAddress.getByName(address)`——它不是"字符串拆成 4 段"，是完整的 JDK 主机名解析：纯数字 IP 快速返回，**非 IP 字符串会走 DNS 查询**。配 `"127.0.0.1"` 的白名单实测：

```
matcher("127.0.0.1").matches("")          = true   ← 空串被 JDK 解析成回环地址
matcher("127.0.0.1").matches("localhost") = true
matcher("127.0.0.1/24").matches("127.1")  = true   ← 缩写十进制被接受, 而 IPUtils.isValidIpV4("127.1") = false, 两处对同一个字符串的判断结果不一致
```

后果：拿它做内网 IP 白名单/管理端限流时，攻击者控制 DNS（或注册一个解析到 127.0.0.1 的域名，SSRF 老手法）即可命中白名单；每次匹配还附带一次 DNS 查询的延迟与抖动。这是 Spring Security 历史同款设计（作者 Luke Taylor 的移植），Spring 后来自己也加了纯 IP 字面量守卫。修法：matches 入口先用 IPUtils.isValidIpV4/V6 挡住非字面量，别把任意字符串喂给 getByName；"127.1" 这类非标格式两处要么都认要么都拒。

### P1-9 DomainUtils 两个实测缺陷：连字符域名解析错 + 嵌套量词指数回溯【实测】

`utils/DomainUtils.java:22-32`：

1. `\w` 不含 `-`，`getDomain("my-site.com", 1)` 实测返回 `site.com`——带连字符的域名（全球 30%+ 域名有连字符）一级域名全提取错。域名段该用 `[-\w.]+`。
2. `(\w*\.?){N}` 是嵌套量词：分段边界不固定，同一段字符可以有多种切法；匹配失败时，正则引擎要把这些切法逐一尝试，耗时随输入长度按指数规律增长。实测数据：level=3、输入 401 个字符（400 个 `a` 加一个 `!`）耗时 6281 毫秒；输入 400 个 `a` 加 `!` 耗时 6932 毫秒；评审代理另构造的 400 字符输入测得 5.9 秒，量级一致。风险：`getDomain` 如果接收用户可控的 Host 头或 Cookie 域，单个请求就能让一个线程长时间占用 CPU——这正是 ReDoS（Regular expression Denial of Service，用特制的正则输入把服务拖垮）。修法：改成显式分段 `([-\w]+\.)+` 后按点号个数截取，或不用正则、直接以 `lastIndexOf` 切分。

### P2-10 HttpMethods 常量类：POST/PUT/DELETE/OPTIONS/TRACE 的值全是 "GET"【读源码+grep 确认】

`constants/HttpMethods.java:17-25` 六个常量复制粘贴没改值。grep 全仓库 `HttpMethods.` 零调用——这个类目前全仓库没有调用方；风险在于常量名与常量值不符——以后如果有人写 `if (method.equals(HttpMethods.POST))` 判断请求方式是否为 POST，即使请求确实是 POST 该条件也永远为假（因为 HttpMethods.POST 的值是字符串 "GET"），且这类错误从现象上很难定位到常量定义处。要么改值要么删文件（和 enums.HttpMethod 重复）。

### P2-11 IPUtils 小毛病一组【实测/代码】

- `IPUtils.java:255`：`log.warn("subnetMask {} should be a number!")` 占位符没传参，日志永远输出字面 `subnetMask {}`，出事时看不到到底是谁不合法。
- `isValidIpV4("192.168.0.1/032")`=true 而 v6 侧拒绝 `/064`——前导零掩码双标【推断·代理实测, 我方读码确认分支差异】。
- `toBinaryStr` 两个私有重载零调用（grep 仅定义处），且 `s = "0" + s` 循环拼串。连同 NetworkConstant、Proto、NetUtils 空壳一起，属"零引用"，建议随孪生清理一并删（commons-spring 的 NetworkConstants 是活的，两者已分叉）。
- `Scheme.of`（enums/Scheme.java:30）：写成了实例方法，`Scheme.of("https")` 编译不过，只能拿一个 Scheme 实例去解析另一个字符串——语义上是静态工厂；解析失败不报错, 直接返回 null。全仓库零调用。

### P2-12 IpAddressMatcher 掩码不校验 + 不记录地捕获异常【实测, 部分修正代理结论】

- 配置串 `"192.168.0.1/abc"` 构造器直接抛 NumberFormatException（在 Spring bean 初始化阶段就报错, 问题能立刻暴露, 尚可接受）；`"/-1"` 不报错，实测 `matches("8.8.8.8")=false`——**修正**：代理说"传 -1 会不声不响退化成全匹配"不对，nMaskBits=-1 命中的是 :62 的"无掩码=精确匹配"分支，退化成精确匹配而非全放行，无安全影响，但构造端应校验 0<=mask<=32（与 IPUtils.isValidSubnetMask 的 1~32 范围保持一致——这里又是一处"两个类对同一件事判断结果不一致"）。
- `matches():54-56` 捕获 IllegalArgumentException 之后不记任何日志直接返回 false，来路不明的脏 IP 查不到痕迹。

### 已越界发现（不在 copilot-networking，顺记）

`copilot-validation/.../IPValidator.java:55-62`：`if (category==IP_V6) {...} else {...}` 的 else 与上一个 `if (category==IP_V4)` 重叠——category=IP_V4 时先算的 v4 结果被 else 分支 `v4||v6` 覆盖，**标了 @IP(V4) 的字段会放行合法 IPv6**。逻辑通过读码确认，建议归入 copilot-validation 的整改清单。
