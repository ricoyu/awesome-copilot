# copilot-orm 模块代码评审报告

> 评审日期：2026-07-16  
> 模块版本：21.0.8（父 POM）  
> 技术栈：Hibernate 6.5.2、Spring Context/Tx、Velocity、Jackson、MySQL  
> 源码规模：`src/main/java` 共 **69** 个 Java 文件；模块内测试 **1** 个测试类

---

## 一、模块概述

`copilot-orm` 是基于 **Hibernate 6** 的 ORM 封装层，对外提供 fluent 风格的数据访问 API。核心入口为 `JpaDao`，通过接口隔离拆分为三类操作：

| 接口 | 职责 |
|------|------|
| `EntityOperations` | 实体 CRUD、批量 persist/save、按主键删除 |
| `CriteriaOperations` | Criteria 快捷查询（按属性、IN、Between 等） |
| `SQLOperations` | 命名 SQL / 原生 SQL（Velocity 动态渲染 + 分页） |

### 包结构

```
copilot-orm/
├── dao/                    # JpaDao、各类 QueryBuilder
├── criteria/               # JPACriteriaQuery 底层实现
├── predicate/              # eq/in/like/between 等条件封装
├── transformer/            # 原生 SQL 结果集 → POJO 映射
├── entity/                 # BaseEntity / 雪花 ID 基类
├── utils/                  # SQLUtils、QueryUtils、JsonUtils
├── interceptor/            # 逻辑删除 / 租户 ID 自动追加
├── directive/              # Velocity 自定义指令
├── generator/              # CopilotSnowflakeIdGenerator
├── converter/              # JPA AttributeConverter
└── exception/              # ORM 异常体系
```

### 核心类职责

| 类 | 说明 |
|----|------|
| `JpaDao` | Spring `@Repository` 统一门面；管理 EntityManager（事务内 `@PersistenceContext`，无事务时 ThreadLocal 自建 EM） |
| `CriteriaQueryBuilder` | Criteria 链式查询，null 条件自动跳过 |
| `NativeSqlQueryBuilder` | 原生/命名 SQL；Velocity 渲染；ORDER BY / LIMIT；count 分页 |
| `CriteriaDeleteBuilder` | Criteria 批量删除 |
| `JPACriteriaQuery` | Criteria 条件组装、分页 count、排序 |
| `ValueHandlerResultTransformer` | 列名 snake_case → camelCase，类型转换，loose/strict 模式 |
| `SQLUtils` | 动态 SQL 缺 WHERE / 多余 AND 的自动修复 |
| `DeletedTenantIdConditionInterceptor` | Hibernate `StatementInspector`，追加 `deleted` / `tenant_id` 条件 |

## 二、问题清单（按严重程度）

### Critical — 需优先修复

#### C-1. 无 Spring 事务时 EntityManager 泄漏

| 项 | 内容 |
|----|------|
| **文件** | `CriteriaQueryBuilder.java`（408–419）、`NativeSqlQueryBuilder.java`（566–577）、`CriteriaDeleteBuilder.java`（86–97） |
| **问题** | 三者在无事务时通过 `entityManagerFactory.createEntityManager()` 创建 EM 并放入 `ThreadLocal`，但**从未 close/remove**。仅 `JpaDao` 提供 `cleanupEntityManager()`，builder 类不会调用它。线程池、异步任务等长生命周期线程会累积未关闭 EM，最终导致连接池耗尽。 |
| **建议** | 抽取统一的 `EntityManagerHolder`（create / close / finally）；builder 在 `findList` / `findPage` / `execute` 的 `finally` 中关闭；或与 `JpaDao.em()` 共用同一套生命周期。 |
| **修复记录（2026-09，P0-7 轮）** | ✅ 已修，按建议第一种方案执行：`CriteriaQueryBuilder.java:27,48`、`NativeSqlQueryBuilder.java:106,130-148`、`CriteriaDeleteBuilder.java:27,41` 统一持 `EntityManagerHolder`，各终结方法（findList/findPage/findOne/execute 等）finally 调 `closeIfNeeded()`（`CriteriaQueryBuilder.java:379,408,416,439,464`、`NativeSqlQueryBuilder.java:267,357`、`CriteriaDeleteBuilder.java:73`）。holder 守卫本身有回归测试 `dao/EntityManagerHolderTest`(3)，其中 R1 修复（本地活跃事务不许 rollback+close）经"撤守卫立刻红"自证。 |

#### C-2. `CriteriaDeleteBuilder` 无事务时必现 NPE

| 项 | 内容 |
|----|------|
| **文件** | `CriteriaDeleteBuilder.java`（47–54、86–97）；`JpaDao.java`（803–804） |
| **问题** | 构造函数只注入 `entityManager`，**未设置 `entityManagerFactory`**。`JpaDao.deleteBy()` 也只传两个参数。无 Spring 事务时 `em()` 调用 `entityManagerFactory.createEntityManager()` → **NullPointerException**。 |
| **建议** | 构造器增加 `EntityManagerFactory` 参数；`JpaDao.deleteBy` 传入 `entityManagerFactory`；与 `CriteriaQueryBuilder` 对齐。 |
| **修复记录（2026-09，P0-7 轮）** | ✅ 已修：`CriteriaDeleteBuilder.java:39-41` 构造器已带 `EntityManagerFactory` 参数并传给 holder；`JpaDao.java:1378-1379` 的 `deleteBy()` 传入三参。集成测试 `it/IntLogicalDeleteTest`、`it/CriteriaQueryTest` 在无 Spring 事务路径下覆盖 deleteBy。 |

#### C-3. `NativeSqlQueryBuilder` 分页 ORDER BY 逻辑写反

| 项 | 内容 |
|----|------|
| **文件** | `NativeSqlQueryBuilder.java`（383–391） |
| **问题** | 注释写「SQL 里已有 ORDER BY 则不再加」，但实现相反：已有 ORDER BY 时追加 `" ORDER BY field dir"`（双 ORDER BY，语法错误）；没有 ORDER BY 时却追加 `" , field dir"`（缺少 ORDER BY 关键字，语法错误）。 |
| **证据** | ```java
if (queryString.toString().toUpperCase().contains("ORDER BY")) {
    queryString.append(" ORDER BY ")  // 应改为 ", "
} else {
    queryString.append(" , ")          // 应改为 " ORDER BY "
}
``` |
| **建议** | 已有 ORDER BY → `append(", " + field + " " + dir)`；无 ORDER BY → `append(" ORDER BY " + ...)`。补充分页排序集成测试。 |
| **修复记录（2026-09，P0-7 轮）** | ✅ 已修，且比建议更彻底（`NativeSqlQueryBuilder.java:590` 起重写的排序拼接方法）：①"已有/没有 ORDER BY"的颠倒分支改正；②旧实现用 `toUpperCase().contains("ORDER BY")` 判断，子查询里的 order by 会误判——新实现做词级扫描，只在括号深度 0（最外层）找 order by 并跳过单引号字符串；③旧实现把排序拼到语句最末尾，SQL 自带 LIMIT/OFFSET/FOR UPDATE 时产出语法错误——新实现定位这些尾部子句起点、把排序插在它们前面。 |

#### C-4. `QueryUtils.enumCodeCondition` 读取 Class 而非枚举实例

| 项 | 内容 |
|----|------|
| **文件** | `QueryUtils.java`（159–175） |
| **问题** | `ReflectionUtils.getFieldValue("code", clazz)` 从 **Class 对象** 取 `code`，而非从 `queryValue` 实例取值。枚举查询条件几乎永远错误或为 null。 |
| **建议** | 改为 `ReflectionUtils.getFieldValue("code", queryValue)`；`code == -1` 表示「查全部」时跳过条件。 |
| **修复记录（2026-09，P0-7 轮）** | ✅ 已修（`QueryUtils.java:167`）：取值对象由 `clazz` 改为 `queryValue` 实例；`:174-182` 补 `code == -1` 跳过条件的检查（javadoc 承诺的"查全部"语义，旧实现会留下恒假条件导致永远查空）。回归测试 `it/QueryUtilsEnumTest`。 |

### Important — 功能缺陷与可靠性

#### I-1. `JpaDao` 无事务 EM 清理回调不可靠

| 项 | 内容 |
|----|------|
| **文件** | `JpaDao.java`（1381–1392、1469–1480） |
| **问题** | 无事务时注册 `TransactionSynchronization.afterCompletion` 清理 EM，但此时往往**没有真实 Spring 事务**，`afterCompletion` 可能永不触发，EM 仍泄漏。 |
| **建议** | 无事务场景用 try-finally 或 Filter/Interceptor 清理 ThreadLocal；不要单独依赖 `TransactionSynchronization`。 |

#### I-2. 动态 ORDER BY 字段未校验 — SQL 注入面

| 项 | 内容 |
|----|------|
| **文件** | `NativeSqlQueryBuilder.java`（383–401、672–682） |
| **问题** | `orderBy` 直接拼入 SQL。若排序字段来自 HTTP 请求且无白名单，存在 **ORDER BY 注入** 风险。 |
| **建议** | 白名单校验（正则 `^[a-zA-Z_][\w.]*$` + 允许列表）；禁止拼接用户原始字符串。 |

#### I-3. 空 IN 列表被替换为字符串 `"''"`

| 项 | 内容 |
|----|------|
| **文件** | `JpaDao.java`（1182–1258）；`NativeSqlQueryBuilder.java`（593–669） |
| **问题** | 空 List/数组时 `params.put(key, "''")`，破坏参数化语义，可能生成 `IN ('')` 等意外 SQL，与 Velocity `#if(!$list.isEmpty())` 推荐写法不一致。 |
| **建议** | 空集合时跳过该条件（Velocity 层处理）或直接返回空结果。 |

#### I-4. 批量 `deleteByPK` 逐条 N+1

| 项 | 内容 |
|----|------|
| **文件** | `JpaDao.java`（436–502） |
| **问题** | 对数组/Collection 循环调用单条 delete（每条 find/merge 或 getReference+remove），大批量删除性能差。 |
| **建议** | 物理删除用 bulk `CriteriaDelete` / `DELETE ... WHERE id IN (...)`；逻辑删除用 bulk UPDATE。 |

#### I-5. `find` / `findIn` 硬编码 `deleted` 字段，忽略配置

| 项 | 内容 |
|----|------|
| **文件** | `JpaDao.java`（617–625、735–751） |
| **问题** | `find()`、`findIn()` 固定 `root.get("deleted")` 和 `root.get("id")`，未使用 `logicalDeleteField` 配置，也未尊重 `logicalDeleteEnabled=false`。实体无 `deleted` 字段时会运行时报错。 |
| **建议** | 统一走 `logicalDeleteEnabled` / `logicalDeleteField` 配置；主键字段用 `@Id` 反射而非硬编码 `"id"`。 |

#### I-6. 依赖 Hibernate 内部字段反射，版本脆弱

| 项 | 内容 |
|----|------|
| **文件** | `JpaDao.java`（908–911、1097–1098、1430）；`NativeSqlQueryBuilder.java`（278、367） |
| **问题** | 通过 `ReflectionUtils.getFieldValue("originalSqlString", query)` 读取命名 SQL 原文，属 **Hibernate 内部实现**，升级易碎。 |
| **建议** | 改用 Hibernate 6 公开 API（`NamedNativeQuery` metadata、`SessionFactory.getNamedQuery()` 等）。 |

#### I-7. `setResultTransformer` 使用已废弃 API

| 项 | 内容 |
|----|------|
| **文件** | `JpaDao.java`（946–948）；`NativeSqlQueryBuilder.java`（320–323、466–469）；`ValueHandlerResultTransformer.java`（39） |
| **问题** | 编译已报 deprecated 警告。Hibernate 6 推荐 `TupleTransformer` / `ResultListTransformer`，未来版本可能移除。 |
| **建议** | 迁移到 Hibernate 6 原生结果映射 API。 |

#### I-8. `SQLUtils` 缓存非线程安全

| 项 | 内容 |
|----|------|
| **文件** | `SQLUtils.java`（13–17、40） |
| **问题** | `SQL_CACHE` 为普通 `HashMap`，并发 `build()` 可能数据竞争。 |
| **建议** | 改用 `ConcurrentHashMap` 或 Caffeine。 |

#### I-9. `CriteriaDeleteBuilder` 可能向 where 传入 null Predicate

| 项 | 内容 |
|----|------|
| **文件** | `CriteriaDeleteBuilder.java`（69–72）；`InPredicate.java`（42–44） |
| **问题** | `InPredicate.toPredicate()` 在 `propertyValues == null` 时返回 **null**，`conditions.add(null)` 后 `executeUpdate()` 可能 NPE 或生成非法 Criteria。 |
| **建议** | `eq` / `in` 在 value 为 null/空时跳过；`execute()` 前过滤 null predicates。 |

#### I-10. 分页 count 与主查询 distinct 不一致

| 项 | 内容 |
|----|------|
| **文件** | `JPACriteriaQuery.java`（518–531） |
| **问题** | 主查询可 `distinct(true)`，但 count 始终 `count(countRoot)` 无 distinct，带 join 时 **totalCount 偏大**。 |
| **建议** | count 使用 `countDistinct` 或与主查询相同的 distinct/groupBy 策略。 |
| **修复记录（2026-09-24）** | `JPACriteriaQuery.list()`：分页 count 改为判断 `criteriaQuery.isDistinct()`——主查询 distinct 时走 `countDistinct(countRoot)`，否则保持 `count(countRoot)`。实测缺陷（H2）：join 一对多集合匹配 4 行、主查询去重后 2 条，修复前 totalCount=3（count 查询根本没 join，条件也没同步）。为此新增一等 API `joinLike(association, property, value)`：在主查询与 count 查询各自实例化 join 条件（谓词不可跨查询复用，见本类 countPredicates 字段区历史教训），并自动给主查询加 distinct。回归测试 `it.PagingCountDistinctTest`（2 用例：join+distinct 计数一致 / 无 join 普通分页不回归），RED（列表 2 条 vs count 3）→ GREEN 2/2。独立评审（deleg_df7e37a8）补充：F6——`setGroupBy` 与分页组合时 count 仍按行数（groupBy 只作用于主查询），全模块当前无该组合调用点，已在 `setGroupBy` javadoc 声明限制；F7——`joinLike` 为 INNER 语义（无匹配子行的父被排除），已写入 javadoc。 |

#### I-11. `deleteByPK(int[])` 循环变量类型不一致

| 项 | 内容 |
|----|------|
| **文件** | `JpaDao.java`（471–491，尤其 476 行） |
| **问题** | 方法签名 `int[] ids`，循环写 `for (long id : ids)`；`requireNonNull(id)` 对 primitive 无意义。 |
| **建议** | 改为 `for (int id : ids)`，删除无意义的 `requireNonNull`。 |

#### I-12. persist/save 批处理后未 clear 持久化上下文

| 项 | 内容 |
|----|------|
| **文件** | `JpaDao.java`（225–249、319–340） |
| **问题** | 注释提到 batch 后应 flush+clear 释放内存，但只 `flush()` 未 `clear()`，大批量写入时 **一级缓存膨胀**，OOM 风险。 |
| **建议** | 每 batch 后 `flush(); em().clear();`。 |

## 三、模块优点

1. **接口隔离清晰**：`EntityOperations` / `CriteriaOperations` / `SQLOperations` 按场景拆分，Service 层可按需注入，降低耦合。
2. **Fluent API 体验好**：Criteria 与 Native SQL 均支持链式调用，null 条件自动跳过（`CriteriaQueryBuilder`）。
3. **Velocity 动态 SQL 生态完整**：自定义 directive（`#ifNotNull`、`#between`、`#ifPresent` 等）+ `SQLUtils` 自动修复，降低动态 WHERE 编写成本。
4. **结果映射能力强**：`ValueHandlerResultTransformer` 支持 loose/strict、MethodHandle、enum 多属性 lookup、@Convert 回退，列名自动 snake_case → camelCase。
5. **批量写入有 flush 节奏**：`batchSize` 可配置，避免单次 flush 过大。
6. **Hibernate 6 批量加载**：`byMultipleIds().multiLoad()` 减少 N+1 主键查询。
7. **逻辑删除/租户拦截器**：`StatementInspector` 统一追加条件，对 Criteria 和 SQL 均生效。
8. **文档详尽**：`readme.md` 覆盖接入配置、Velocity 语法、分页、枚举、多线程无事务场景等，对使用者友好。

## 六、总结

`copilot-orm` 在 **API 设计**（接口隔离 + fluent 风格）和 **动态 SQL 能力**（Velocity + SQLUtils + 结果映射）上成熟实用，文档也较完整。但存在三类需关注的问题：

1. **资源生命周期**：无事务场景下 EntityManager 在 builder 类中创建却未关闭，是最高优先级的生产风险。
2. **确定性 Bug**：分页 ORDER BY 逻辑写反、`CriteriaDeleteBuilder` 无事务 NPE、`enumCodeCondition` 读错对象——这些会在特定调用路径下直接失败或产生错误数据。
3. **测试债务**：69 个源文件仅 1 个测试类且只覆盖 `SQLUtils`，核心 DAO 路径缺乏回归保护，重构与升级 Hibernate 风险高。

建议优先修复 **Critical** 四项，并为核心 builder 补充集成测试后再做 Hibernate API 迁移。
