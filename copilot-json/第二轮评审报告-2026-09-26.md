# copilot-json 第二轮评审报告（2026-09-26）

> 评审对象：JsonPathUtils「解析一次、读多次」改造的未提交改动（git diff 共 6 文件）。
> 评审方式：两个新上下文的独立评审代理（逻辑正确性 + 并发性能各一），全部发现由实现人逐条复核后处置。
> 标签：【实测】= 本机探针复现；【评审人实测】= 评审代理复现且实现人复核过证据；【推断】= 代码路径分析。
> 背景数据与修复主体见《高并发与大数据量分析报告.md》「第二轮复检（2026-09-26）」章节。

## 总体回答：高并发大数据量下能不能正常工作？

- **死锁：没有。** 全模块仅两把锁，均为一次性或已绕开。
- **吞吐瓶颈：确认存在且已修**——不是锁，是收 String 的每个公共入口每次调用都把整篇文档从头解析一遍（40KB 报文 466µs、2MB 报文 41.5ms，路径求值只占 0.2-0.5µs）。新增 `parse()` + DocumentContext 重载后，5 字段一组 2.36ms→0.48ms；32 线程复用 ctx 读 2,089 万 ops/s。
- **本轮新发现的真正并发问题**：json-path 3.0.0 函数路径的编译产物跨文档并发会串数据（评审人实测 48 万次错 10.4 万次、0 异常），已按规避方案修复并配回归测试。

## 一、评审发现与处置（按严重度）

### E1【评审人实测·P0】List.class 的修复不成立，本地全绿是 m2 旧 jar 造成的假绿 → 已修

- 位置：`JsonPathUtils.convertValue`；关联 `commons-lang/.../ValueHandlerFactory.java:639-641`。
- 现象：commons-lang 工作区源码里 `determineAppropriateHandler(List.class)` 返回 `StringListValueHandler`（非 null），而它 `convert(List)` 只认 String、遇 List 直接 return null。我写的 `if (valueHandler == null) return mapped` 保护对 List.class 走不到。新测试在源码构建 commons-lang 的环境里必红；我本地绿是因为 classpath 上放的是 D:/.m2 里 09-23 的旧 jar（旧 jar 的单参方法里没有 List 分支，该分支是 09-23 晚间提交 9cca489 才加的）。
- 复核：实现人用 javap 对照两个产物的 `determineAppropriateHandler` 字节码（m2 jar 无 `java/util/List` 引用、target/classes 有 2 处），成立。
- 修复：`convertValue` 改为「mappingProvider 产物已是目标类型（含 Map/List 深拷贝副本）时直接返回；handler 结果为 null 时回退 mapped」。验证流程改为先 `mvn -pl commons-lang install -DskipTests` 再跑 copilot-json，消除假绿；10 用例在源码构建下全绿。

### E2【评审人实测·P1】快速路径使 Double/double 目标「看 JSON 数字写法决定成败」 → 已修

- 现象（评审人探针）：`readNode(json,"$.price",Double.class)` 在 5.5（Double 节点）返回 5.5、在 5（Integer 节点）返回 null；`double.class` 两种输入都 null（`clazz.isInstance` 对基本类型恒 false）。同一次调用一半有值一半 null，比旧版统一 null 更难排查。
- 根因：`DoubleValueHandler.convert` 只认 Float/BigDecimal，Double 入参 throw（`ValueHandlerFactory.java:171-190`）。
- 复核：实现人读 handler 源码确认，成立。
- 修复：`wrapPrimitive` 处理基本类型映射 + mapped 已是目标包装类型时直接返回；补参数化用例 `testReadNodeDoubleTargetAcrossTokenTypes`（5.5/5 × Double.class/double.class 四组合 + Integer 反向断言）。

### R2-E1【评审人实测·P0】函数路径编译产物跨文档并发串值（json-path 库级缺陷） → 已规避 + 配测试

- 现象：8 线程、两份报文交替读同一 path `$.nums.sum($.nums)`，48 万次中 104,365 次拿到另一份报文的参数值，0 异常 0 null。
- 根因（评审人读 json-path 3.0.0 源码）：`FunctionPathToken.java:66-87` 在求值期写共享编译产物的 `Parameter.lateBinding/evaluated` 字段（非 volatile）。
- 定性：旧版 PATH_CACHE 同样有此问题，属既有风险；本次新增 API 让共享编译实例的用法变多，触发面更大。评审人实测 `length()`、`$..name`、过滤器路径只读安全；`append()` 按库源码（`Append.java:25`）会直接写文档树，属写操作。
- 修复：`JsonPathCache.compiled` 对含 `(` 的 path 不进缓存、每次 compile（实测 2.6-6.5µs/条，代价可控）；回归用例 `testFunctionPathsCompiledPerCallNotShared`（8 线程 × 2 报文 × 2 万次，断言 0 串值）。

### R2-E3【评审人实测·P1】path 首尾空白两入口行为不一致 → 已修

- 现象：`JsonPathUtils.readNode(ctx,"  $.meta.count  ")` 返回 null（PathCompiler 的 InvalidPathException 被捕获后返回 null），同一个 ctx 的 `ctx.read("  $.meta.count  ")` 能读到 3。两入口共用一份缓存后，同一逻辑路径两种键、两种结果。
- 修复：`JsonPathCache.compiled` 内统一 `path.trim()`；补用例 `testReadNodeWithPathWhitespaceConsistent`。

### R2-E4【属实·P2】注释里的「1/N」是未填数字的占位符，冒充实测 → 已改

- 实现人原话核查：确是我写的占位表述，评审代理实测该锁差距约 5-8 倍（4 线程热点 476万 vs 2340万 ops/s；64 path 轮转 192万 vs 1590万），注释已换成实测数字。教训：注释里的数字也必须是测出来的。

### E3【评审人实测·P2】「旧入口语义不变」说法不精确 → 维持修复目的, 变更记录已补

- 现象：目标类型为 Map/Object/CharSequence/BigInteger 时，旧版恒返回 null（NPE 被捕获），新版返回真实转换结果。
- 处置：这正是 E1 要修的缺陷，「语义不变」收窄为「解析与读取路径语义不变，无 handler 目标类型由恒 null 变为有值」；⚠️ 提醒业务代码里 `if (readNode(...,Map.class) == null)` 这种把 null 当「路径不存在」的判断分支会走到另一侧。

### E4【属实·P3】`instanceof Number` 把可变子类当不可变 → 已收紧

- 现象：`AtomicInteger/AtomicLong/LongAdder` 都 extends Number 且可变，Jackson 解析产物不含它们，但 `ctx.set(...)` 可写入共享树，快速路径会把可变共享实例直接交给调用方。
- 修复：白名单收紧为 String/Boolean/Character/Integer/Long/Double/Float/Short/Byte/BigDecimal/BigInteger 具体类。

### E5【评审人 javac 复现·P4】重载引入源码级不兼容 → 部分修复 + 发布说明

- 现象一：`readNode(null, path)`（第一参写死 null 字面量）在新重载下编译报「引用不明确」。仓库内 grep 零处受影响；对外无法用类型手段消除，已写入报告 ⚠️ 源码兼容性（显式 `(String) null` 即可）。
- 现象二：外部拿 `com.jayway.jsonpath.DocumentContext`（如官方 `JsonPath.parse()` 产物）或 `ReadContext` 变量传不进自定义子接口参数 → **已修**：ctx 重载参数类型改用父接口 `com.jayway.jsonpath.DocumentContext`，两种类型都能传。

## 二、评审建议的处置（非阻塞）

| 建议 | 处置 |
|---|---|
| 旧 String 入口委托后，路径读取失败的 error 日志不再带报文摘要 | 接受收缩：`SUPPRESS_EXCEPTIONS` 下 ctx 重载的 catch 实际只剩「path 表达式编译失败」，那是代码问题与报文无关；解析失败的日志仍在 `parse()` 里带 jsonSummary。理由已写入报告 |
| `JsonPathCache` 缺 clear() | 已加（javadoc 写明进程级共享状态、仅测试隔离/排查用） |
| 注释实测数字偏乐观（评审机 40KB parse≈294-350µs vs 本机 466µs） | 属实（跨机 ±40% 漂移）。报告与注释改为区间/比率表述；比率结论（≈5 倍、展开占四成以上）两机一致 |
| `ctx.read(path, filters...)` 不再缓存是性能回退 | 仓库内零调用点维持不缓存（旧缓存键依赖 Predicate.toString 不稳定），注释写明权衡 |

| 并发用例应升级为「多线程 × 多报文 × 函数路径」 | 已按此形态实现（R2-E1 回归用例） |
| 把「ctx 并发读取安全」的措辞收窄 | 已改：parse javadoc 与类注释限定为「属性/通配/过滤器路径并发读安全，函数路径已由缓存层规避」 |
| 环境既有红：JSONTest/JsonPathUtilsTest/JacksonUtilsTest 共 6 错为读 `d:/msg_data*.json` 等本机不存在的 2018 年数据文件；NoDefaultConstructorTest 为已登记的缺 `-parameters` 旧问题 | 与本次改动无关（改动前基线同样红），不背锅不修，属测试资产迁移的另案 |

## 三、正面结论（评审代理确认，可放心依赖）

1. `readPath` 与旧实现逐字节同义（只换了取编译产物的方式）；`SUPPRESS_EXCEPTIONS` 下确定路径未命中返回 null、不确定路径未命中返回空 List，两入口一致。
2. Caffeine `get(key, JsonPath::compile)` 实测 16 线程 + 人为放慢 loader 时同 key 只编译 1 次（"at most once per key" 成立），命中均摊 0.017µs，无全局锁热点。
3. 属性/通配路径共享同一颗解析树并发读安全（评审人 32 万次压测错乱 0），「解析一次读多次」的核心承诺成立。
4. Map/List 目标类型返回的是 mappingProvider 的深拷贝副本，不暴露 ctx 共享树（评审人用身份比较确认）。
