# copilot-json 高并发与大数据量分析报告

> 分析对象：`JacksonUtils`（序列化/反序列化）、`JsonPathUtils`（JSONPath 解析）及其支撑类。
> 分析日期：2026-09-14。环境：JDK 21.0.11 / Jackson 2.18.2 / json-path 3.0.0（根 pom.xml:50,54）。
> 每条结论标注验证状态：【实测】= 本机跑探针复现，附原始输出；【推断】= 代码路径分析，附确认方法。
> 探针源码在 `copilot-json/target/probesrc/`（一次性产物，不在 git 内），可随时删除。

## 总体结论（先回答你的问题）

1. **没有死锁风险。** 全模块只有两把锁：`ObjectMapperFactory` 的一次性双检锁（初始化后永远不再进入），和 json-path 库自带 LRU 缓存的 `ReentrantLock`（只出现在遗留方法 `JsonContext.read(String)` 里，`JsonPathUtils` 主入口已经绕开它）。8 线程压 `readNode` 热点路径实测 68,487 ops/s，线程数上去吞吐不掉，没有互相等待的痕迹。
2. **共享 ObjectMapper 本身并发安全**（Jackson 的 formatter 有 clone 保护，实测并发 Date 序列化结果全对、加速比 3.16）。但**它外面包的工具类有三处会出错**：一处共享 `SimpleDateFormat`（并发下解析出错误日期且不报错）、一处 `JSON.cleanup` 预处理会改坏合法 JSON、一处失败路径把整个报文写进日志（坏数据风暴时拖垮线程池）。
3. **大数据量的问题不是卡死，是内存放大 + 日志放大。** 10 万条对象的列表序列化实测把 9MB 数据放大成约 102MB 堆占用（11 倍）；2MB 的坏 JSON 解析失败一次耗时 425ms，其中绝大部分是把整串写日志的开销。

下面按修复优先级列出全部发现。

## P0：生产环境可直接触发、且产生错误数据

### P0-1 ✅已修复(2026-09-14) 共享静态 SimpleDateFormat `SDT_GMT`：并发反序列化日期时静默出错值【实测】

- 位置：`commons-lang/.../constants/DateConstants.java:315`（定义）；被 `DateUtils.java:333、754` 使用；
  入口链在 copilot-json 这边是：
  - `DateStr2LongDeserializer.java:42` → `DateUtils.parse(source)`
  - `DateDeserializer` / `LocalDateDeserializer` / `LocalDateTimeDeserializer.java:97` → `DateUtils.toLocalDateTime(string)`
- 现象（探针2 原始输出，8 线程并发 `DateUtils.parse` HTTP 格式日期串 "Sun, 06 Nov 1994 08:49:37 GMT"）：

  ```
  [SDT_GMT] 调用=120000 错值/异常=921 30s内完成=true 耗时ms=3967
     样本: Sun, 06 Nov 1994 08:56:22 GMT -> Sun Nov 06 16:06:22 CST 1994 (期望 16:56:22)
     样本: Sun, 06 Nov 1994 08:56:23 GMT -> Sun Nov 06 16:56:28 CST 1994 (期望 16:56:23)
     样本: Sun, 06 Nov 1994 08:56:24 GMT -> Sun Nov 06 16:46:24 CST 1994 (期望 16:56:24)
  ```

  另有对照实验（同一实例裸并发 `format`）：`[裸共享SDF] 16万次格式调用出错次数 = 6703`。
- 原因：`SimpleDateFormat` 内部有可变状态（`Calendar` 实例），设计上就不是线程安全的（它自己的 javadoc 明说）。`SDT_GMT` 是 `public static final`，被 `DateUtils.parse` 的兜底分支和 `toLocalDateTime` 的兜底分支直接调用，没有任何同步或 clone。`SimpleDateFormatHolder`/`DateFormatterHolder` 对其它格式都做了 ThreadLocal 隔离，唯独漏了这个常量。
- 影响：多线程同时反序列化 RFC1123 格式日期（HTTP 头、部分第三方 API 返回体）时，约 0.7% 的调用拿到错的日期（分钟级到小时级偏差），**不抛异常、不报日志**，业务层完全无感知。数据量小、并发低时几乎撞不上——这正是"正常少量数据表现良好"的原因之一。
- 怎么改：`SDT_GMT` 改成 `DateTimeFormatter.RFC_1123_DATE_TIME`（线程安全），或者按 `SimpleDateFormatHolder` 已有的 ThreadLocal 模式包一层。改动点在 commons-lang，但受益方是 copilot-json 的四个日期反序列化器。

> **修复记录（2026-09-14）**：`DateConstants.SDT_GMT` 改为 `ThreadLocal<SimpleDateFormat>`（`ThreadLocal.withInitial`，GMT 时区设置移进工厂 lambda，格式串复用已有常量 `FMT_RFC1123_FORMAT`）；`DateUtils.java:333/754` 两个调用点改成 `SDT_GMT.get().parse(...)`。选 ThreadLocal 而非 `DateTimeFormatter.RFC_1123_DATE_TIME` 的原因：后者对带自定义时区缩写的容忍度与 SDF 不完全一致，且 `SimpleDateFormatHolder` 本来就是 ThreadLocal 模式，行为零漂移优先。
> - 复测（同一验收探针，8线程×15000次）：`调用=120000 错值/异常=0（修复前=921）`。
> - 回归测试：新增 `commons-lang SdtGmtConcurrencyTest` —— 修复后通过；`git stash` 回退旧代码后同一测试变红（能抓 bug）。
> - ⚠️ 行为变更：`SDT_GMT` 类型变了（`SimpleDateFormat` → `ThreadLocal<SimpleDateFormat>`）。**对仓库内**：全仓库 grep 只有 DateUtils 两处调用，已同步改完，编译器会点名所有调用点。**对仓库外**（commons-lang 是发布的 public API）：这是源码+二进制双破坏——外部若有 `SDT_GMT.parse(...)` 直调，重编译会报错（可发现），但**不重编译直接换 jar 会在运行时抛 `NoSuchFieldError`**（评审指出，上轮"无静默风险"的说法只对仓库内成立）。发布时按破坏性变更记 changelog，或给外部下游一个 `@Deprecated` 过渡方法。ThreadLocal 里的实例每线程一个、线程数封顶即数量封顶，无线程池泄漏问题（探针确认）。

### P0-2 ✅已修复(2026-09-14) `JSON.cleanup` 会改坏一切含转义双引号的合法 JSON【实测】

- 位置：`copilot-json/.../json/JSON.java:58-63`；调用点 `JsonPathUtils.java:92`（每次 `parseJson` 都无条件执行）。
- 现象（探针5 原始输出，输入是完全合法的 JSON，一个字段值里带 `\"` 转义）：

  ```
  [cleanup] 原串        = {"note":"he said \"hi\"","embedded":"{\"a\":1}","t":"$.a"}
  [cleanup] cleanup之后 = {"note":"he said "hi"","embedded":{"a":1},"t":"$.a"}
  [cleanup] readNode($.note)      = "null" (期望: he said "hi")
  [cleanup] readNode($.embedded)  = null
  [cleanup] readNode($.t)         = null
  ```

  整串被改成语法非法，`SUPPRESS_EXCEPTIONS`（`JsonPathUtils.java:74`）把报错吞掉，所有读取统一变成 `null` / 空列表。
- 原因：`cleanup` 用三次无边界的全串 `replace`（`\"`→`"`、`"{`→`{`、`}"`→`}`）来"解开内嵌 JSON 字符串"。它无法区分"值里正常转义的引号"和"被序列化成字符串的整段 JSON"。任何 `\"` 都会先被解掉，从第一个含转义的字段起，后面的所有字段全部损坏。
- 影响：这是功能正确性缺陷，跟并发无关，但它解释了另一件事——你的 JSONPath 解析对"恰好没有转义引号"的数据表现良好。同时它也是 `JsonPathUtils` 全部方法的公共税：每次调用先做 3 遍全串扫描（13KB 的样例实测无感，几 MB 的报文每次多出几毫秒固定开销，见 P2-4）。
- 怎么改（二选一，推荐后者）：
  1. 直接删掉 `cleanup` 调用——标准 JSONPath 本来就能读到内嵌 JSON 字符串的值，调用方拿到 String 再自己 `toObject`；
  2. 保守做法：先 `objectMapper.readTree` 试解析，**解析成功就原样使用**，只有失败时才尝试 cleanup 修复（把"破坏性预处理"降级为"坏数据抢救"），并在日志里区分标记。

> **修复记录（2026-09-14，后经独立评审补修）**：`JsonPathUtils.parseJson` 重写为三步（比原方案2更进一步，兼顾了 `$.billJson.FBillNo` 这类穿透老用法）：
> 1. **原样解析**（不再预先 cleanup）。成功 →
> 2. **Map/List 树级展开**：递归遍历 provider 解析产物（`JacksonJsonProvider.parse` 返回 `LinkedHashMap`/`LinkedList` 树，不是 JsonNode），字符串值能整体严格解析（`FAIL_ON_TRAILING_TOKENS`）为 JSON 文档的，替换成解析出的子 Map/List；引号开头的循环剥字符串化层（层数与字符串化链共用一个预算）。**深度预算只计"字符串化展开次数"，原生 Map/List 下钻不计数**（评审发现按树深计数会让 >5 层业务嵌套里的内嵌 JSON 和根级字符串化文档丢失穿透能力，已修）；根节点本身是字符串时先解一层。只有"严格合法的 JSON 文档"才被提升，`he said \"hi\"`、`{name}` 模板串原样保留。
> 3. 原样解析**失败** → 才跑 `JSON.cleanup` 抢救（保留老代码对截断/双重转义脏数据的兼容），成功时打 WARN 标记是修复路径。
> `JSON.cleanup` 本身未删（`JsonPathUtils` 的抢救分支和外部直接调用者还在用）。
> - 复测（FixProbe，全绿）：转义引号 JSON `$.note=he said "hi"`、`ifExists=true`（修复前 null/false）；内嵌穿透 `$.billJson.FBillNo=XSCK001`；坏数据抢救 `$.billJson.x=1`；模板串不被误提升。
> - 回归测试：新增 `copilot-json JsonPathUtilsCleanupTest`（6 用例全过）；既有 `JsonPathUtilsTest2`（childTask 深层取值）、`JsonPathUtilsStressTest`（32线程并发正确性+吞吐）、`JacksonUtilsTest`（18）全部通过。
> - ⚠️ 行为变更一：取"整棵内嵌JSON子树"时（`readNode(json,"$.billJson")`），过去拿到的是原始字符串，现在拿到的是展开后的 Map —— 若业务代码把该返回值直接当 String 用，需改为 `JacksonUtils.toJson(obj)` 或改读具体叶子路径。
> - ⚠️ 行为变更二：`JsonPathUtils` 热路径不再对每个字符做 3 遍全串 replace，13KB JSON 压测 6.8万→ ops/s 持平或更好（树级展开只处理 `{`/`[` 开头的字符串值，正常业务 JSON 几乎零命中）。
> - 大坑记录：第一版实现按 `JsonNode` 树写展开逻辑，测试探针发现 `JacksonJsonProvider.parse` 产出的是纯 Map/List（内部 `readValue(json, Object.class)`），`instanceof JsonNode` 分支根本不进——幸好探针先跑了一遍，改对形态后全绿。

## P1：并发/大数据下的可靠性与性能问题

### P1-1 ✅已修复(2026-09-14) 解析失败路径把整个报文写进日志：坏数据风暴时一条 400ms+【实测】

- 位置：`JacksonUtils.java:64`（`log.error("将JSON串\n{}\n转成{}失败", json, ...)`）、`106`、`139`、`154`；`isValidJson` 的 `JacksonUtils.java:291`（`log.error("", e)`）；`JsonPathUtils.java:101`（`parseJson` 失败路径打 JSON 摘要——这一处已经改对了，只打 128 字符预览 + 长度 + hashCode，见 `JsonPathUtils.java:141-151`，是正面样板）。
- 现象（探针4 原始输出）：

  ```
  [失败路径] 2MB 非法JSON toObject 一次耗时=425ms (主要花在 log.error 把整串写日志)
  [成功路径] 同尺寸合法JSON readValue(JsonNode) 一次耗时=3ms
  ```

- 原因：logback 默认同步 ConsoleAppender（测试配置 `logback-test.xml:5-10` 同款；生产若是同步 FileAppender 行为一样），`log.error` 会走完整格式化 + 落盘；而且**整条异常链还会再打一次堆栈**，`{}` 占位符对 2MB 字符串做无差别拷贝。
- 影响：并发场景下如果上游偶发喂坏数据（截断的响应、乱码），这不是"慢一点"而是正反馈：失败→刷大日志→线程被日志 IO 占住→更多超时→更多失败。大数据量 + 高并发时最危险的一条。
- 怎么改：学 `JsonPathUtils.jsonSummary` 的做法，把所有 `log.error` 里的原始 JSON 换成「长度 + 前 128 字符 + hashCode」；确需全文时降到 DEBUG 级别并用 `isDebugEnabled()` 包住。

> **修复记录（2026-09-14）**：`JacksonUtils` 新增私有 `jsonSummary(String)`（长度+hash+前128字符），`toObject(String,Class)`、`toMap`、`toGenericMap`、`toList`、`readTree` 五处 catch 全换成摘要；`toJson`/`toBytes`/`writeValue` 的 error 日志补上"对象类名/失败动作"上下文（原来只有 `log.error(e.getMessage(), e)` 看不出在干什么）；`toObject(byte[],Class)` 不打报文内容；`isValidJson` 从"打整条堆栈"降为 DEBUG 摘要（调用方要的就是布尔值，非法 JSON 是业务常态）。
> - 复测（同尺寸 2MB 坏串，3 次取最小）：**5ms**（修复前 425ms，约 85 倍）。
> - ⚠️ 行为变更：失败日志里不再出现完整 JSON 原文。排查偶发坏报文需要全文时，开 `com.awesomecopilot.json` 的 DEBUG 拿到摘要+堆栈，或临时在调用点自行打印。

### P1-2 ✅已修复(2026-09-14) `java.util.Date` 字段往返丢毫秒，且静默【实测】

- 位置：`ObjectMapperDecorator.java:173-174`（`setDateFormat(new SimpleDateFormat("yyyy-MM-dd HH:mm:ss"))`）+ `ObjectMapperDecorator.java:176`（`WRITE_DATES_AS_TIMESTAMPS` disable，所有 Date 走字符串格式）。
- 现象（探针3 原始输出）：

  ```
  [Date往返] 输入毫秒=1726286400123 JSON={"date":"2024-09-14 12:00:00"} 还原=1726286400000 无损=false
  ```

- 影响：带毫秒的时间戳（日志时间、雪花关联时间）toJson→toObject 一圈回来差最多 999ms。并发混合压测里"错误 480000"全部由这一条造成（见下），不是线程安全问题，是精度问题。做缓存值序列化（copilot-cache 全走这里）、和外部系统对时间戳时会有隐性偏差。
- 怎么改：格式里带上 `.SSS`，或把 `copilot.jackson.epochBased` 设为 true 走毫秒数（配置分支已存在：`ObjectMapperDecorator.java:77-81`）。属于行为变更，要配合下游一起改。

> **修复记录（2026-09-14）**：`ObjectMapperDecorator:173` 的 `setDateFormat` 改为 `yyyy-MM-dd HH:mm:ss.SSS`。光改输出格式会读不回来——`DateUtils.parse` 的正则识别链（`SimpleDateFormatHolder`/`DateFormatterHolder` 各两个入口，共 4 处）原先没有任何带毫秒的模式，会掉进兜底分支返回 null。已新增常量 `PT_ISO_DATETIME_MILLIS`/`FMT_ISO_DATETIME_MILLIS`/`DTF_ISO_DATETIME_MILLIS`，并在 4 条识别链开头插入带毫秒分支（`DateUtils.parse`、`toLocalDateTime`、以及带时区的两个重载都覆盖到）。
> - 复测：`{"date":"2024-09-14 12:00:00.123"}` 往返 `1726286400123` 无损；旧的秒级串 `2024-09-14 12:00:00` 仍正常解析（向后兼容）；Map 内嵌 Date 也带毫秒。
> - 回归测试：新增 `JacksonUtilsDateTest`（3 用例：毫秒往返、旧串兼容、Map 内 Date）。
> - ⚠️ 行为变更（重要）：Date 序列化结果从 `"2024-09-14 12:00:00"` 变成 `"2024-09-14 12:00:00.123"`。三种下游要提前确认：① 前端若用严格 `YYYY-MM-DD HH:mm:ss` 解析这个字段会报错；② 已落库的 JSON 快照不受影响（读取端兼容），但**新写入的串变长**，字段长度按 19 字符设计的库表列会溢出；③ 任何对本框架输出做字符串相等比较的测试/对账逻辑都要同步。
> - 未选 `epochBased=true` 的原因：那会把所有 Date 输出从字符串改成数字，影响面比加毫秒段大得多，且 `jackson.properties` 里现在是 false，等于强行改全局策略。

### P1-3 混合并发吞吐基线【实测】（正面结论）

- 32 线程 × 3 万次混合调 `toObject/toJson/toMap/toList`：`420,755 ops/s，异常=0`；"错误"48 万条经探针3定位为 P1-2 的毫秒截断，非并发问题。
- 16 线程并发 `readTree`（含 500 元素数组）48,000 次：`结果错乱=0 异常=0`。
- Date 序列化 16 万次：`单线程 379ms | 8线程并发 120ms（加速比 3.16），并发结果一致=true`。说明 Jackson 2.18 对 `setDateFormat` 实例每次 clone 并有 `AtomicReference` 复用（依据：`DateTimeSerializerBase._serializeAsString` 源码 2.9 起的行为，本机 2.18.2 sources jar 确认），所以**这条没有共享 SimpleDateFormat 问题，不要自己再加 synchronized**。

### P1-4 Spring 环境下 `decorate` 会二次改造全局 ObjectMapper bean【推断】

- 位置：`JacksonUtils.java:43-47`（static 块拿 `ObjectMapperFactory.createOrFromBeanFactory()` 再 `decorator.decorate(...)`）+ `ObjectMapperFactory.java:38`（Spring 环境直接返回容器里的 bean）。
- 原因：Spring Boot 自动配置出来的 `ObjectMapper` bean 同时被 Spring MVC 的消息转换器持有。copilot-json 在静态块里对它 `registerModule`、`setDateFormat`、`setVisibility`、`configure(...)`，等于把整个应用的 HTTP JSON 行为一起改了；反过来，如果 Spring 侧在你之后再配置一次，你的工具行为也会被改。两个持有者都能写、无人协调。
- 触发确认方法：任意 Boot 应用引入本模块，请求一个含 Date 的接口，看响应时间格式是否变成 `yyyy-MM-dd HH:mm:ss` 且带毫秒截断——是，则污染已被观察到。
- 怎么改：工具类永远 `copy()` 一份再装饰（`objectMapper.copy().registerModule(...)`），或干脆不碰容器 bean、自建单例；如需和 Web 层一致，让 Spring bean 反过来引用工具类这一个。

### P1-5 ✅已修复(2026-09-14) `decorate` 在 `registerModule` 之后继续改同一个 module 实例【推断，优先级低于 P1-4 但要一起改】

- 位置：`ObjectMapperDecorator.java:166-168`：先 `objectMapper.registerModule(javaTimeModule)`，紧接着 `javaTimeModule.addDeserializer(LocalDateTime.class, new LocalDateTimeDeserializer(epochMilisFormatter))`。
- 原因：`SimpleModule` 的 setup 是懒执行的，注册后再往 map 里塞，多数情况下能生效、但属于依赖库内部时序的未定义行为；而且第一次真正反序列化 LocalDateTime 之后 Jackson 有缓存，之后再改就不生效了。这里恰好"注册前的 149 行放了一个 formatter 版、注册后又放了一个 epoch 版"，两个都往同一 key 塞，最终生效的是竞态后写入的那个——目前代码能跑对只是顺序凑巧。
- 怎么改：把 module 装配完整（所有 addSerializer/addDeserializer 都做完）之后再调用一次 `registerModule`。

> **顺带修复记录（2026-09-14，随 P2-7 一并处理）**：`stringBasedObjectMapper` 里"注册后再往同一个 JavaTimeModule 塞第二个 LocalDateTime 反序列化器"已删除。查证过 `LocalDateTimeDeserializer` 无参构造（epoch毫秒formatter版）内部对字符串 token 走 `DateUtils` 自动识别、对数字 token 按毫秒解析——两条路本来就通，旧代码先塞的 `ofPattern` 版实际被后塞的 epoch 版覆盖，最终生效的一直是 epoch 版；现在直接在注册前放入 epoch 版（`new LocalDateTimeDeserializer()`），只留一次注册，行为不变、消除时序依赖。既有断言（`JacksonUtilsTest` 的 `"2020-07-23 14:12:22"` 字符串、epoch 数字用例）全绿佐证。

### P1-6 ✅已修复(2026-09-14) 大对象内存放大：树 + 字符串双份驻留【实测】

- 探针2：10 万个元素的列表，`toJson` 产物 9MB，期间堆增量约 102MB（≈11 倍，主要是序列化中间 char/byte 缓冲与最终 String）；`toPrettyJson` 5 千条输出 699KB、29ms（`writerWithDefaultPrettyPrinter` 每次新建 writer，见 `JacksonUtils.java:205`）。
- `toPrettyJson(String)` 分支（`JacksonUtils.java:201-203`）更糟：字符串先用 org.json 完整 parse 一遍再输出，等于同一份数据三份驻留，而且 org.json 与 Jackson 的合法性判定不一致（探针3 输出：`toPrettyJson("{bad")` 抛的是 `org.json.JSONException`，不是 `JacksonException`，异常类型不可预期）。
- 影响：单次无感；高并发各自抱着几 MB 报文时，堆峰值 = 并发数 × 报文 × 11，直接换来 GC 风暴/Full GC 停顿。没有锁，但吞吐会因此掉。
- 怎么改：大对象走 `writeValue(Writer, ...)`（`JacksonUtils.java:212`，流式）或 `toBytes`；`toPrettyJson` 的 prettyWriter 做成静态常量复用。

> **修复记录（2026-09-14）**：两处
> 1. `prettyWriter` 提升为 `volatile` 字段 + 双检惰性初始化（不能在 static 块里直接建——那时 mapper 还没装饰完），`toPrettyJson` 不再每次 `writerWithDefaultPrettyPrinter()` 新建 writer。
> 2. `toPrettyJson(String)` 分支从 `new JSONObject(s).toString(2)`（org.json 全量 parse，多份驻留 + 抛 `JSONException`）改走全局 mapper：`readTree` → 缓存的 prettyWriter，异常类型统一成 `JacksonException`。
> 3. `toPrettyJson` 的 javadoc 写明大对象慎用、指向流式 `writeValue`。
> - 复测：对象/字符串两条路径输出都能 `readTree` 回读；坏串 `{bad` 现在抛 `JacksonException`（修复前 `org.json.JSONException`）。
> - ⚠️ 说明：10 万元素 `toJson` 的 9MB/102MB 放大比**没有改善也没法在工具层改善**——那是 Jackson 序列化写 `String` 的固有行为（中间 char[] 扩容 + 最终 String 拷贝）。这条的正解是业务侧改走 `writeValue(Writer)` 流式输出，或开 `epochBased`。本条修的是能修的部分（重复建 writer、双 JSON 库、异常类型）。

### P1-7 ✅已修复(2026-09-14) `JsonPathUtils` 解析与转换用了两个不同配置的 mapper【推断→已实测】

- 位置：`JsonPathUtils.java:68`（`new JacksonJsonProvider()`——无参构造内部自建一个裸 `ObjectMapper`）与 `JsonPathUtils.java:69`（`new JacksonMappingProvider(JacksonUtils.objectMapper())`——用装饰过的）。
- 影响：`ALLOW_SINGLE_QUOTES`（`ObjectMapperDecorator.java:115`）、日期装饰等只作用于"转换"阶段，"parse"阶段不吃这套配置：单引号 JSON 在 `JacksonUtils.toObject` 里合法、在 `JsonPathUtils.readNode` 里直接进失败分支返回 null。两处行为不一致，排查起来很费时间。
- 怎么改：`new JacksonJsonProvider(JacksonUtils.objectMapper())`（该 provider 有收 mapper 的构造器）。
- 附：`JsonPathUtils.java:64-75` 的静态 `CONFIG` 本身线程安全（json-path 3.0.0 的 `addOptions/setEvaluationListeners` 都返回新对象、不改自身，已从 sources 确认）；`PATH_CACHE` 用 `ConcurrentHashMap.computeIfAbsent`（`JsonPathUtils.java:109-120`）正确且无全局锁，8 线程 8 万次全对。遗留方法 `JsonContext.read(String)`（`JsonContext.java:71-77`）还会走 json-path 全局 LRUCache（`ReentrantLock`），公开入口 `JsonPathUtils` 已绕开——但 `JsonContext` 是 public 的，外部若拿到 `DocumentContext` 直接 `read(path)` 仍会进那把锁，建议在 `JsonContext` 里也改走 `PATH_CACHE`。

> **修复记录（2026-09-14）**：`CONFIG` 静态块改为 `new JacksonJsonProvider(JacksonUtils.objectMapper())`，parse/转换两端共用同一装饰 mapper。复测：单引号串 `{'name':'John'}` 经 `readNode` 能读出 `John`（修复前 null），常规双引号路径不受影响。回归测试：`JsonPathUtilsCleanupTest.singleQuotedJsonParsesSameAsJacksonUtils`。
> ⚠️ 附带收益：`P0-2` 修复里的内嵌 JSON 展开、`JsonContext` 遗留锁问题不在本条范围，未动。

### P1-8 ✅已修复(2026-09-14) `PATH_CACHE` 无界：动态拼接的 path 会造成缓慢内存泄漏【推断】

- 位置：`JsonPathUtils.java:109`。`computeIfAbsent` 永不驱逐。若业务 path 形如 `$.list[?(@.id==' + id + ')]`（把变量拼进表达式），每个新 id 都进缓存，key 无上限。
- 触发确认：grep 业务代码里传给 `readNode` 系列的 path 是否含字符串拼接/变量插值；500 个不同 path 的压测（探针/已有 `JsonPathUtilsStressTest`）只证明性能没问题，不证明容量没问题。
- 怎么改：换成带 `maximumSize` 的 Caffeine（commons-lang 已依赖 caffeine，`ReflectionUtils.java:68` 在用），或先确认 path 都是代码里写死的字面量，再在注释里立规矩。

> **修复记录（2026-09-14）**：`PATH_CACHE` 从 `ConcurrentHashMap` 换成 `Caffeine maximumSize(20_000)`（`copilot-json/pom.xml` 显式声明 caffeine 依赖，走父 pom dependencyManagement 的 3.2.0）。超上限按 W-TinyLFU 驱逐，代价只是重新 compile 一次。复测（8 线程 × 1 万次 readNode，混 1/7 动态 path 压驱逐）：结果正确 80000/80000；纯热点两轮 47,270 / 73,864 ops/s（旧 CHM 基线 68,487，热 JIT 后持平或更好，无回退）。
