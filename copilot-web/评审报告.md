# copilot-web 模块评审报告

- 评审日期：2026-09-16
- 对象版本：git HEAD（a3f7cc9）
- 依赖：Spring Framework 6.1.5 / Spring Boot 3.x / Jakarta Servlet 6 / JDK 21
- 范围：copilot-web 全部 25 个主类 + 2 个测试类
- 标注说明：【实测】= 本机探针程序跑出真实输出佐证；【读码】= 通读源码 + grep 交叉验证得出的结论；【推断】= 由代码路径推导、需要特定环境才能确认，并注明何种环境可验证。
- 用词约定：全文用平实技术语言，不用比喻性、口号性词汇。

## 总体判断

copilot-web 的分层是清楚的：advice 负责异常→统一 Result，http/filter 负责请求包装，converter/resolver 负责参数绑定，utils 提供 REST 输出与工具。骨架合理。但存在三类问题：

1. 若干"写了但没生效"的能力（XSS 防护整条链路无人装配、CORS 通配符因拼接 bug 输出成非法值）——README 宣称的能力与实际运行结果不一致，这类最危险，因为使用方以为已经防护/配置好了。
2. 若干"生效但会误伤"的逻辑（XSS 清洗删掉正常业务文案、重复读包装破坏 JSON 里的换行）。
3. 一批正确性/性能打磨项（双重日期处理、异常处理器每次反射查 Bean、MessageHelper 懒加载竞态）。

下面按严重程度编号。

---

## P0（当前代码里已成立、影响接口正确性或安全能力的缺陷）

### P0-1 CORS.allowAll() 生成的响应头是非法的 [*]，通配符失效【实测】

```java
// CORS.java:96
response.setHeader(HEADER_ACCESS_CONTROL_ALLOW_HEADERS, joinWith(", ", allowedHeaders));
// allowAll() 里 allowedHeaders 是 List<String>, 内容 ["*"]
```

- 现象（探针输出，代理一个 HttpServletResponse 记录 setHeader 的值）：
  ```
  Access-Control-Allow-Headers = [*]
  Access-Control-Allow-Origin  = [*]
  Access-Control-Allow-Methods = [*]
  ```
  正确值应当是 `*`，实际发出去的是 `[*]`（带方括号）。
- 原因：这里的 `joinWith` 是 commons-lang 自研的 `StringUtils.joinWith(String, Object...)`（静态导入 CORS.java:10）。传入一个 List 时，List 被当作可变参数的一个元素，Guava Joiner 对它调用 toString，得到 `[` + 内容 + `]`。
- 影响：`Access-Control-Allow-Origin: [*]` 不是浏览器认可的取值，跨域预检与放行都不会生效。而 RestUtils 的四个 writeJson/download 都调 allowAll()（RestUtils.java:65/85/105/163），也就是说依赖它做跨域的接口实际处于"以为开了跨域、其实没开"的状态。
- 建议：`build()` 里改用 `String.join(", ", allowedHeaders)`（JDK 标准，接收 Iterable），或 commons-lang3 的 `StringUtils.join(allowedHeaders, ", ")`。

### P0-2 XSS 清洗会删掉正常业务文案里的括号词【实测】

```java
// XssCleanUtils.java:24
Pattern.compile("(?<!href=')\\s*(eval|alert|confirm)\\s*\\([^)]*\\)\\s*(?!')", ...)
```

- 现象（探针输出）：
  ```
  输入: {"desc":"本模型 alert(risk) 指标偏高"}
  输出: {"desc":"本模型指标偏高"}
  ```
  `alert(risk)` 连同前面的空格被整体删除，正常句子被改坏。（同一探针里 `(confirm)` 因前面没有空格而侥幸保留，说明命中与否取决于书写格式，行为不稳定。）
- 原因：该规则想清除"纯文本里的恶意函数调用"，但 eval/alert/confirm 也是普通英文词，出现在任何正文、字段说明、AI 提示词里都会被删。而真正的 XSS 拦截靠的是前几条标签规则，删纯文本函数名并不能防 XSS（不渲染成 HTML 时 alert(x) 本就无害；要渲染时应做的是输出转义，不是输入删除）。
- 影响：用户提交的文本、后台配置、含这些词的消息模板会被不声不响地改写，属于数据被篡改，且难以定位。
- 建议：删除第 6 条 PLAIN_TEXT_MALICIOUS_FUNC 规则；防 XSS 用"存储原文 + 输出时按上下文转义"（模板引擎的 escape / StringEscapeUtils.escapeHtml4），把清洗限定在标签与协议层。

### P0-3 XSS 防护与可重复读过滤器没有任何装配入口，能力实际未启用【实测·grep 全仓库】

- grep 全仓库：`new XssHttpServletRequestWrapper(` 零命中（该类只在自身定义处出现）；`new HttpServletRequestRepeatedReadFilter(`、`@Component`/`@WebFilter`/`FilterRegistrationBean` 也都没有指向它们。ExceptionFilter、TraceFilter 情况相同（TraceFilter 有 @Component，但依赖组件扫描到该包才生效，需确认）。
- 影响：README 第 2.x 节宣传"XSS 防护与请求体重复读取"，但当前若没有下游 starter 手工装配，这两个过滤器不会进过滤器链，防护是落空的。安全能力"代码在但没跑"比"没有该功能"更危险——审计时会误判为已防护。
- 建议：确认 copilot-spring-cloud-starter / security-starter 是否装配；若没有，补一个 `@AutoConfiguration` 注册 `FilterRegistrationBean<XssFilter>`，并在 README 标注"需引入 starter 或在 web.xml/FilterRegistrationBean 显式注册"。同时 XssHttpServletRequestWrapper 目前也没有配套 Filter（只有 wrapper 没有 filter 类），需要补 XssFilter。

## P1（正确性与可靠性问题，特定输入/时序下出错）

### P1-1 重复读包装会破坏 JSON：读 body 后删掉其中的换行与制表符【读码】

```java
// RepeatedReadHttpServletRequestWarpper.java:48
data = WebUtils.bodyString(request).getBytes(UTF_8);
// WebUtils.java:50
return sb.toString().replaceAll("\r|\n|\t", "");
```

- 机制：`WebUtils.bodyString` 逐行读并用 `replaceAll` 删除回车/换行/制表字符。用它缓存请求体时，凡是字符串值内部含换行（多行文本、带 `\n` 转义之外的真实换行、日志正文）的 JSON，重新组装出来的 body 已经和原始字节不一致。
- 触发条件：任何走 HttpServletRequestRepeatedReadFilter 的 JSON 请求，且字段值里含真实换行。
- 影响：下游签名校验、反序列化得到的内容与客户端原始内容不一致；对"重复读用于安全审计/签名"的用途尤其致命。
- 补充：该 wrapper 的 `isFinished()`/`isReady()` 恒返回 false（RepeatedRead...java:69/74），异步读（非阻塞 IO）下语义错误；GET 等无 body 请求也会白白在构造函数里读一次输入流。
- 建议：缓存 body 直接按字节读原始 InputStream（`request.getInputStream()` → byte[]），不要经过 bodyString 的字符串清洗；isFinished 用 `bias.available()==0`。

### P1-2 MessageHelper 懒加载有竞态与异常穿透，且调用方拿到 null 无提示【读码】

```java
// MessageHelper.java:28-35（其余四处同构）
if (messageSource == null) {
    synchronized (MessageHelper.class) {
        messageSource = ApplicationContextHolder.getBean(MessageSource.class); // 无二次判空
        if (messageSource == null) return null;
    }
}
```

- 问题①（双检锁不完整）：进入 synchronized 后没有再判一次 `messageSource == null` 就直接取 Bean；高并发首个请求时多个线程会依次进锁重复 getBean（虽然结果幂等，但失去双检锁意义）。字段是 volatile，无可见性问题，属于"退化成串行重复获取"。
- 问题②（异常穿透）：`ApplicationContextHolder.getBean(MessageSource.class)` 在没有 MessageSource 时抛的是 `NoSuchBeanDefinitionException`（Spring 行为），不是返回 null——`if (messageSource == null) return null` 基本到不了。于是没有配 MessageSource 的应用，第一次调用 getMessage 直接抛异常，被 RestExceptionAdvice 当成未知异常返回 500。注释里想做的"取不到就用默认消息"没实现。
- 问题③（重载歧义）：LocalizedException.java:115 调 `MessageHelper.getMessage(messageTemplate, messageParams)`，messageParams 是 `List<Object>`，精确匹配到 `getMessage(String, List<Object>)`（MessageHelper.java:61）——这条其实走对了；但同类 `getMessage(code, args...)` 的可变参数重载在只传一个 List 时会把整个 List 当成单个 arg。存在两类重载混用，易错。
- 影响：i18n 未配置或消息 key 不存在时，异常处理器里再抛异常，用户看不到有意义的错误信息。
- 建议：synchronized 块内二次判空；用 try/catch NoSuchBeanDefinitionException 包 getBean 并保持 messageSource 为 null 走 defaultMessage 分支；把"取不到 MessageSource"降级为返回 code 或 defaultMessage，而不是抛。

### P1-3 CustomConversionService 每次枚举转换都新建 converter，绕开父类缓存【读码】

```java
// CustomConversionService.java:27-31
protected GenericConverter getConverter(TypeDescriptor sourceType, TypeDescriptor targetType) {
    if (Enum.class.isAssignableFrom(targetType.getObjectType())) {
        return new GenericEnumConverter(properties); // 每次调用都 new
    }
    return super.getConverter(sourceType, targetType);
}
```

- 影响：Spring 的 ConversionService 对 converter 有缓存，这里命中枚举分支时每次转换都 new 一个 GenericEnumConverter，白建对象；每个请求里凡是有枚举参数/字段的绑定都会触发。属于性能问题，不是功能错误。
- 另需确认：覆写 getConverter 拦截所有目标为 Enum 的转换，会覆盖掉 DefaultConversionService 内建的其他枚举转换路径（如 String→Enum 默认按 name），行为改变范围要看下游是否依赖内建枚举转换。
- 建议：缓存一个 GenericEnumConverter 实例（properties 不变时复用），或改走 addConverterFactory 注册而非覆写 getConverter。

### P1-4 日期参数存在两套并行处理，Resolver 会覆盖 @DateTimeFormat【读码】

- GlobalBindingAdvice.java:33-39（@ControllerAdvice + @InitBinder 给 Date/LocalDate/LocalDateTime/LocalTime 注册 PropertyEditor）与 resolver/ 下四个 HandlerMethodArgumentResolver 同时存在。
- 冲突：@InitBinder 的编辑器作用于 `@ModelAttribute`/表单对象字段绑定；ArgumentResolver 作用于方法级 `@RequestParam Date xxx`。DateArgumentResolver.supportsParameter 对任何 Date 子类参数返回 true（DateArgumentResolver.java:26），且它排在 Spring 内建 resolver 之前时会优先命中——开发者在参数上写的 `@DateTimeFormat(pattern=...)` 会被忽略（DateArgumentResolver 直接走 `DateUtils.parse`，不看注解）。
- 影响：同一个应用里日期解析有两套规则，方法参数上的 @DateTimeFormat 不生效且没有任何提示，"写了格式化注解却不生效"很难排查。
- 建议：ArgumentResolver 里先读 `parameter.getParameterAnnotation(DateTimeFormat.class)`，有注解优先按注解；或明确二选一（保留 @InitBinder 或保留 Resolver），不要同时装配。DateArgumentResolver 里两个 Pattern 常量（ISO_DATETIME_PATTERN/ISO_DATE_PATTERN）定义了但整个类没使用，一并删除。

### P1-5 RestUtils：跨域开关是 static 可变字段、download 全量进内存【读码】

- enableCors（RestUtils.java:45）是 `static boolean`，在 static 块从 yaml 读取。问题：① 若被运行期改写，是全局可变状态，无可见性/原子性保障（虽 boolean 写入原子，但语义上不该可变）；② 默认 true（yamlOps.getBoolean(..., true)）——与"网关和本服务两端都开跨域会冲突"的注释矛盾，等于默认就打开这个有冲突风险的开关。
- download(File, filename)（RestUtils.java:174-175）：`IOUtils.readFileAsBytes(file)` 把整个文件读进内存再 `out.write`。下载大文件（几十 MB 以上、并发多个）会明显推高峰值内存，甚至 OOM。
- 影响：内存型风险，文件越大越危险。
- 建议：enableCors 改 final 或用配置注入；download 用流式拷贝（`Files.copy(path, outputStream)` 或 IOUtils.copy(in, out) 带缓冲），并支持 Content-Length / Range。

### P1-6 ObjectToEnumConverterFactory 只按属性匹配，不覆盖 name/ordinal，行为与 GenericEnumConverter 不一致【读码】

- ObjectToEnumConverter.convert（ObjectToEnumConverterFactory.java:42-52）只遍历 properties 调 `lookupEnum(enumType, source, property)`，全 null 就返回 null。而 GenericEnumConverter 会再 fallback 到按 name/ordinal 匹配（GenericEnumConverter.java:70）。
- 两个类名字相近、职责重叠但行为不同：前者在没配 properties 时（默认空 Set）永远返回 null，等于"注册了却什么都不转"。
- 建议：统一到一套枚举转换实现；ObjectToEnumConverterFactory 至少补 name/ordinal fallback。

## P2（性能、一致性、可维护性）

### P2-1 RestExceptionAdvice.handleThrowable 注释与代码矛盾，且每次都反射式查 Sentinel Bean【读码+实测】

```java
// RestExceptionAdvice.java:367-382 注释说 "加了 handleThrowable 则 Sentinel 熔断规则不生效"
// 但方法体实际是: sentinelExists 时 Tracer.trace(e) 然后仍自己处理返回, 并没有"直接重新抛出"
@ExceptionHandler(Throwable.class)
@ResponseStatus(value = HttpStatus.OK) // 强烈建议 500，不要再用 200！  ← 注释与上一行取值自相矛盾
```

- 矛盾①：类注释（354-366 行）描述的策略（"有 RestBlockExceptionHandler 就直接抛出让过滤器处理"）与当前实现（trace 后自己返回 Result）不一致，后来者无法判断哪个是对的。
- 矛盾②：`@ResponseStatus(HttpStatus.OK)` 与方法上方"强烈建议 500"的注释直接冲突；findRealCause 末尾确实返回 500（RestExceptionAdvice.java:447/451），但 @ResponseStatus(OK) 作用在方法上，二者对非 RuntimeException 分支可能给出不同码。
- 性能：`applicationContext.getBean("restBlockExceptionHandler")`（431 行）在处理未捕获异常的最终路径上，每个错误请求都做一次容器查找 + 三次 `Tracer.trace(e)`（373/427/437 重复）。sentinelExists 一旦被置 true 后走 373 行分支，但 431 行的 getBean 每次仍执行（sentinelExists 只影响 trace，不影响是否 getBean）。
- 建议：让注释与实现一致（重新抛出 vs 自行处理，二选一并写清）；启动时解析一次 `restBlockExceptionHandler` 是否存在并缓存 boolean，别在异常路径查容器；去掉重复的 Tracer.trace。

### P2-2 六处空日志消息 `log.error("", e)`【读码】

- RestExceptionAdvice.java:258/266/290/302/311 用 `logger.error("", e)`；275 用 `log.info("", ex)`。消息为空串，日志检索时这些行没有关键词，排障困难。
- 另：该类同时使用继承来的 `logger`（父类字段）和自建的 `log`（74 行）两个 Logger，命名不统一（如 100 行 logger.info、166 logger.info、275 log.info），维护易混。
- 建议：补上有意义的消息（哪个接口/什么异常类型），统一用一个 logger。

### P2-3 上传超限处理方法未覆写父类同名方法，可能不生效；ACTUAL_SIZE_PATTERN 被转义腐蚀【读码】

- handleMaxUploadSizeExceededException（RestExceptionAdvice.java:333）没有 `@Override`，方法名与父类 ResponseEntityExceptionHandler 的 `handleMaxUploadSizeExceededException` 拼写一致但少了 6.1 里的 `@ExceptionHandler` 绑定；父类该方法是 protected 且已被 @ExceptionHandler 注解，这里重名不带注解是否被调用需实测确认。若未被调用，上传超限会走父类默认处理，自定义的"解析实际大小/限制大小填进 i18n 消息"逻辑形同虚设。
- `ACTUAL_SIZE_PATTERN`（86-87 行）源码里是 `.*size\s{1}\(...\).*maximum\s{1}\(...\)$`，注意 `\\s` 经 Java 字符串转义后为 `\s`（正确）。但结尾 `$` 要求整段以 maximum(...) 结束，Tomcat 实际消息后面可能还有内容，`matches()` 会不命中——【推断，需真实 MaxUploadSizeExceededException 消息验证】。
- 建议：加 `@Override` 并跑一个上传超限的集成用例确认自定义分支被进入；正则改 `find()` 或放宽结尾。

### P2-4 HttpMessageNotReadable（请求体格式错误）返回 500 而非 400【读码】

- RestExceptionAdvice.java:164-170：handleHttpMessageNotReadable（JSON 反序列化失败，属客户端错误）里 `Results.status(INTERNAL_SERVER_ERROR)` 且 HTTP 状态 `HttpStatus.INTERNAL_SERVER_ERROR`。客户端传坏 JSON 却收到 500，语义错误，且会让网关/熔断把客户端错误计入服务端失败率。
- 建议：改 BAD_REQUEST + HttpStatus.BAD_REQUEST。

### P2-5 TraceFilter：traceId 生成方式弱且 MDC 不清理【读码】

```java
// TraceFilter.java:37
traceId = String.valueOf(APP_ID + Math.abs(new Random().nextInt(MAX_TRACE_ID)));
```

- 问题①：每个新请求 `new Random()`，无谓对象分配且种子来自系统时间，短并发下有撞车概率。
- 问题②：`MDC.put("traceId", ...)`（39 行）后没有在 finally 里 `MDC.remove("traceId")`。Tomcat 线程复用，下一个请求若自带 TRACE_ID 会覆盖（无害），但异步/无 filter 收尾的路径可能让上一个请求的 traceId 残留到别的日志。
- 问题③：APP_ID 是 `100*1000000`，`+nextInt(1000000)` 结果约一亿多，量级没问题，但 int 溢出风险在于 APP_ID 随实例累加（虽当前是常量 100）；注释说"支持最大 100 个微服务"，实际用 `100 * MAX` 固定，多实例部署时不同实例可能生成相同 traceId。
- 建议：复用 commons-lang 的 `SnowflakeId`（javap 确认 `public synchronized long nextId()` 可直接 new 复用），或 ThreadLocalRandom；doFilter 用 try/finally 清理 MDC。

### P2-6 ExceptionFilter 把异常塞进 ThreadContext 但无人读取，依赖 Listener 收尾清理【读码】

- ExceptionFilter.java:42 `ThreadContext.put(ROUTE_CAUSE, e)`，grep 全仓库无任何地方 `ThreadContext.get(ROUTE_CAUSE)`。它的作用退化为"往 ThreadLocal 塞一个异常引用"，靠 ThreadLocalCleanupListener 在请求结束清理，否则线程池复用会泄漏（listener 已注册则安全，需确认注册）。
- 建议：若无消费方，去掉 ROUTE_CAUSE 塞入，或补上读取方（如响应写出时把根因放进诊断头）。

### P2-7 CORS.allowAll() 缺 allowCredentials 与 Vary 头【读码】

- build() 只写三个 Access-Control-* 头（CORS.java:95-98），`Access-Control-Allow-Credentials` 不处理、不写 `Vary: Origin`。allowAll 用 `*` 时本就不能与 credentials 同用（浏览器规则），语义上没错，但对"带 Cookie 的跨域"这种常见需求，allowAll 无法工作且无提示。
- 建议：补一个 allowCredentials(origin, ...) 分支（回显具体 Origin + Vary: Origin），并在文档说明 `*` 与 credentials 互斥。

### P2-8 XssCleanUtils.cleanObject 对 List 元素无效（只处理 String[] 和 Iterable 遍历但丢弃结果）【实测】

```java
// XssCleanUtils.java:68-73
if (value instanceof Iterable<?>) {
    for (Object obj : iterable) cleanObject(obj); // 递归结果被丢弃, 且没替换进集合
}
```

- 探针实测：`List.of("<script>...", "plain")` 经 cleanObject 后元素 0 仍是原文（含 script）；而 String[] 分支（就地赋值）清洗成功。Iterable 分支没有把清洗结果写回集合（对不可变 List 也写不回）。
- 影响：如果依赖 cleanObject 清洗 List 参数，安全过滤不生效且没有任何报错。
- 建议：该方法要么明确只支持 String/数组并在遇到 List 时抛异常提示不支持，要么改用可写 List 的 `ListIterator.set`。

### P2-9 HeaderMapRequestWrapper.addHeader 实际是覆盖（put），getHeaders 语义与名字不符【读码】
